# Payment System

> Accept card payments for an e-commerce platform through a payment service provider (PSP), guarantee money moves **exactly once**, and keep books that always balance.

## Requirements

### Functional
- Charge a customer for an order (pay-in); later pay out sellers (pay-out).
- Refunds and partial refunds.
- Handle asynchronous results from PSPs (webhooks), 3-D Secure challenges.
- Internal wallet/balances and a complete audit trail.

### Non-functional
- **Correctness above everything:** no double charges, no lost payments.
- Reliability and fault tolerance; every failure must be recoverable and explainable.
- Security & compliance (**PCI DSS**): never store raw card numbers yourself.
- Moderate throughput: 1M transactions/day ≈ 12 TPS avg — correctness, not scale, is the hard part.

## API

```http
POST /v1/payments
Idempotency-Key: 5f1c2a0e-…            ← generated by the client per checkout attempt
{ "order_id": "o-981", "amount": 4999, "currency": "USD", "payment_method": "pm_tok_123" }

201 Created  { "payment_id": "pay_77", "status": "PENDING" }
GET  /v1/payments/pay_77
POST /v1/payments/pay_77/refunds   { "amount": 1000 }
POST /v1/webhooks/psp               ← PSP → us, signature-verified
```

Amounts are **integers in minor units** (cents) — never floating point.

## Data model

```text
payments        (payment_id, order_id, idempotency_key UNIQUE, amount, currency,
                 status, psp_reference, created_at, updated_at, version)
payment_events  (payment_id, from_status, to_status, reason, ts)           -- audit trail
ledger_entries  (entry_id, txn_id, account_id, debit, credit, currency, ts) -- append-only
accounts        (account_id, type[customer|merchant|platform_fees|psp_clearing], balance)
```

Use a relational DB with ACID transactions (PostgreSQL) — correctness beats horizontal scale at this volume.

## Payment state machine

```text
CREATED → PENDING → (REQUIRES_ACTION) → SUCCEEDED
                  ↘ FAILED
SUCCEEDED → PARTIALLY_REFUNDED → REFUNDED
```

Every transition is a conditional update (`UPDATE … SET status='SUCCEEDED' WHERE id=? AND status='PENDING'`) plus an event row, in one transaction.

## High-level design

1. Checkout calls the **Payment API** with an **Idempotency-Key**.
2. The idempotency store returns the stored response if the key was seen before (and rejects concurrent in-flight duplicates).
3. **Payment service** creates the payment record (`CREATED → PENDING`), calls **risk/fraud** scoring.
4. **Payment executor** calls the **PSP** with a card *token* (the PSP or a vault holds actual card data; the page uses the PSP's hosted fields/SDK so card numbers never touch our servers).
5. The PSP responds synchronously and/or via **webhook**. The webhook handler verifies the signature and publishes `PaymentSucceeded` / `PaymentFailed`.
6. Consumers update the **ledger** (double-entry) and **wallet balances**, and notify the order service.
7. **Reconciliation** compares our ledger with the PSP's daily settlement files.

## Deep dives

### Idempotency — exactly-once effect
- Client generates one key per checkout attempt and reuses it on retries.
- Server: `INSERT … (idempotency_key) ON CONFLICT DO NOTHING`, then either process or return the stored result.
- We pass our `payment_id` as the idempotency key **to the PSP**, so our retries don't double charge either.
- Every consumer of payment events is idempotent (dedupe by event ID).

### Handling unknown outcomes
Timeouts are the dangerous case: did the PSP charge or not?
- Never assume failure. Mark the payment `UNKNOWN`/`PENDING` and **query the PSP** by reference (or wait for the webhook).
- Retry with the same PSP idempotency key — safe by construction.

### Double-entry ledger
Every movement of money creates balanced entries that sum to zero:

| Account | Debit | Credit |
| --- | --- | --- |
| Customer (card via PSP clearing) | 49.99 | |
| Merchant payable | | 47.49 |
| Platform fee revenue | | 2.50 |

- The ledger is **append-only**; corrections are new reversing entries, never updates.
- Balances are derived (or cached and verifiable) from entries.
- Invariant checks: sum of all entries = 0 per transaction.

### Reconciliation
- Nightly (or more often), ingest PSP settlement reports and match line by line against ledger entries.
- Mismatches (missing webhook, amount/currency differences, chargebacks) go to an exceptions queue for automated fixes or finance ops review.
- Reconciliation is the final safety net for every bug above it.

### Distributed transactions across services
Order, payment, inventory, and wallet live in different services; use a **saga** (orchestrated by the payment service or a workflow engine like Temporal) with compensating actions (release inventory, refund), and the **transactional outbox** pattern so a DB update and its event are published atomically.

### Pay-outs
Batch merchant payouts on a schedule after holding periods; each payout is itself an idempotent payment with ledger entries.

### Security
- Tokenisation via PSP; minimise PCI scope.
- Encrypt sensitive data at rest; strict access controls and audit logs.
- Verify webhook signatures and timestamps; replay protection.
- Fraud signals: velocity checks, device fingerprinting, 3-D Secure for risky payments.

## Scaling & reliability

- 12–100 TPS fits comfortably on a well-tuned primary DB with replicas; shard by merchant if needed later.
- Use a durable queue for events; retries with backoff; dead-letter for manual review.
- Multi-PSP routing: fail over or route by cost/success rate per card type/region.

## Trade-offs

- **Sync vs async confirmation:** synchronous gives better UX; async (webhooks) is the source of truth. Use both.
- **Strong consistency** is non-negotiable for balances and ledger; analytics can be eventual.
- **Build vs buy:** PSPs abstract card networks; you still own idempotency, ledger, and reconciliation.
