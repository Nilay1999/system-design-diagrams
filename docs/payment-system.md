# Payment System

> Accept card payments for an e-commerce platform through a payment service provider (PSP), guarantee money moves **exactly once**, and keep books that always balance.

## The problem in one minute

A payment system's traffic is modest — a million payments a day is about 12 per second — but the cost of a mistake is real money and real trust. The hard problems are all about **correctness under failure**:

- A request times out. Did the card get charged or not? Retrying might charge twice; not retrying might lose a sale or leave a customer charged without an order.
- The PSP tells us the result twice (synchronously and by webhook), or out of order, or not at all.
- Several services (orders, inventory, wallet, payouts) must agree on what happened.
- Months later, finance asks why the books are off by ₹12,000.

The answers are a small set of disciplined patterns: **idempotency keys at every hop**, an explicit **state machine** with conditional transitions, an **append-only double-entry ledger**, the **transactional outbox** for events, and daily **reconciliation** against the PSP's and bank's records as the safety net.

| Decision | Choice | Why |
| --- | --- | --- |
| Card data | PSP-hosted fields / tokenisation; we only see tokens | Keeps us out of most PCI DSS scope |
| Duplicate protection | Client idempotency key → our payment; our `payment_id` → PSP idempotency key | No double charges from any retry |
| Status | State machine with conditional updates and an event history | Webhooks, pollers and retries can't corrupt state |
| Money tracking | Double-entry, append-only ledger in the same transaction as the status change | Books always balance; full audit trail |
| Timeouts | Treat as "unknown", query the PSP, retry with the same key | Never guess |
| Events | Transactional outbox → Kafka, idempotent consumers | No lost or phantom events |
| Safety net | Daily reconciliation with PSP settlement files and bank statements | Catches every bug above it |
| Store | One PostgreSQL primary (+ replicas) | ACID matters more than horizontal scale at this volume |

## Requirements

### Functional

- **Pay-in:** charge a customer for an order (cards, plus wallets/UPI through the PSP).
- **Refunds:** full and partial.
- **Pay-out:** pay sellers their balance on a schedule, minus fees.
- Handle asynchronous PSP results (webhooks) and customer authentication (3-D Secure).
- Internal balances (merchant payable, platform fees) and a complete audit trail.
- Multiple PSPs for redundancy and cost.

### Non-functional

| Property | Target |
| --- | --- |
| Correctness | No double charges; no lost payments; ledger always balances |
| Durability | Every state change recorded and explainable |
| Availability | 99.99 % for the payment API; failures recoverable without manual data surgery |
| Security | PCI DSS compliance; never store raw card numbers; signed webhooks |
| Latency | Synchronous response in ~1–3 s (dominated by the PSP and 3-D Secure) |
| Scale | ~1 M payments/day (12 TPS average, ~100 TPS peak) |

## Capacity estimation

- **Payments:** 1 M/day ≈ **12 TPS** average, ~100 TPS at sales peaks.
- **Writes per payment:** payment row + 3–5 state events + 3–4 ledger entries + outbox + idempotency record → ~15 rows. At 100 TPS that's ~1,500 row writes/s — comfortable for one PostgreSQL primary.
- **Storage:** ~2 KB per payment including history and ledger → 2 GB/day ≈ 0.7 TB/year. Ledger data is kept for years (regulations often require 7–10).
- **Webhooks:** roughly 2–3 per payment → ~300 webhooks/s at peak.

**Scale is not the hard part; correctness is.** Choose boring, strongly consistent technology.

## API

```http
POST /v1/payments
Idempotency-Key: ik-5                      # generated by the caller once per checkout attempt
Content-Type: application/json

{ "order_id": "o-981", "amount": 499900, "currency": "INR",
  "payment_method": "pm_tok_123", "capture": "automatic",
  "return_url": "https://shop.example/checkout/return" }

201 Created   { "payment_id": "pay_77", "status": "SUCCEEDED" }
202 Accepted  { "payment_id": "pay_77", "status": "REQUIRES_ACTION", "next_action": { "redirect_url": "…" } }
402 Payment Required  { "payment_id": "pay_77", "status": "FAILED", "decline_code": "insufficient_funds" }
409 Conflict  { "error": "request_in_progress" }      # same key, still processing
422 Unprocessable { "error": "idempotency_key_reused_with_different_body" }
```

```http
GET  /v1/payments/pay_77
POST /v1/payments/pay_77/refunds    Idempotency-Key: rf-1    { "amount": 100000, "reason": "item_missing" }
POST /v1/webhooks/{psp}             # PSP → us; signature + timestamp verified
```

**Money is an integer in minor units** (499900 paise = ₹4,999.00), never a float: `0.1 + 0.2 != 0.3` in floating point, and rounding errors in money are bugs.

## Data model

```sql
CREATE TABLE idempotency_keys (
  key            TEXT PRIMARY KEY,
  caller_id      TEXT NOT NULL,
  request_hash   TEXT NOT NULL,         -- detect the same key reused with a different body
  status         TEXT NOT NULL,         -- IN_PROGRESS | COMPLETED
  response       JSONB,
  created_at     TIMESTAMPTZ,
  expires_at     TIMESTAMPTZ            -- e.g. 24 h
);

CREATE TABLE payments (
  payment_id     TEXT PRIMARY KEY,
  order_id       TEXT NOT NULL,
  amount         BIGINT NOT NULL,       -- minor units
  currency       CHAR(3) NOT NULL,
  status         TEXT NOT NULL,
  psp            TEXT,
  psp_reference  TEXT UNIQUE,
  outcome_known  BOOLEAN NOT NULL DEFAULT true,
  version        INT NOT NULL,
  created_at     TIMESTAMPTZ, updated_at TIMESTAMPTZ
);

CREATE TABLE payment_events (           -- audit trail of every transition
  payment_id TEXT, seq INT, from_status TEXT, to_status TEXT, source TEXT, payload JSONB, ts TIMESTAMPTZ,
  PRIMARY KEY (payment_id, seq)
);

CREATE TABLE ledger_entries (           -- append-only
  entry_id   BIGSERIAL PRIMARY KEY,
  txn_id     TEXT NOT NULL,             -- groups balanced entries
  account_id TEXT NOT NULL,
  debit      BIGINT NOT NULL DEFAULT 0,
  credit     BIGINT NOT NULL DEFAULT 0,
  currency   CHAR(3) NOT NULL,
  payment_id TEXT,
  created_at TIMESTAMPTZ NOT NULL
);

CREATE TABLE accounts (
  account_id TEXT PRIMARY KEY,
  type       TEXT,                      -- psp_clearing | merchant_payable | platform_fee_revenue | …
  currency   CHAR(3)
);

CREATE TABLE outbox (event_id TEXT PRIMARY KEY, type TEXT, payload JSONB, published_at TIMESTAMPTZ);
CREATE TABLE processed_webhooks (psp TEXT, event_id TEXT, PRIMARY KEY (psp, event_id));
```

## High-level architecture

See the [Architecture](#diagram/architecture) diagram.

| Component | Responsibility |
| --- | --- |
| PSP hosted fields / SDK | Collects card details in the browser and returns a token; card numbers never reach our servers |
| Payment API | Authenticates callers, validates requests, claims idempotency keys |
| Payment service | Owns the state machine, the saga with the order service, and the outbox |
| Risk / fraud | Scores payments; decides when to require 3-D Secure or block |
| PSP executor | Calls the chosen PSP with `payment_id` as its idempotency key; routes between PSPs |
| Webhook handler | Verifies signatures, deduplicates, applies transitions |
| Payments DB | Payments, events, idempotency, outbox |
| Ledger | Double-entry, append-only; balances derived from entries |
| Kafka + consumers | Order service, wallet, payouts, notifications — all idempotent |
| Reconciliation | Matches our ledger against PSP settlement files and bank statements |

## A card payment

See [Card payment](#diagram/pay-in).

1. The browser collects card details in the PSP's hosted fields and gets a token (`pm_tok_123`).
2. Checkout calls `POST /payments` with an idempotency key it generated for this checkout attempt.
3. The API inserts the key as `IN_PROGRESS`. If the key exists and is `COMPLETED`, it returns the stored response; if it's `IN_PROGRESS`, it returns `409`; if the body differs, `422`.
4. It creates the payment (`CREATED → PENDING`) and asks risk/fraud for a score.
5. The executor calls the PSP, passing **our `payment_id` as the PSP's idempotency key**.
6. If the PSP requires 3-D Secure, the payment becomes `REQUIRES_ACTION` and the caller redirects the customer to their bank.
7. The PSP sends a signed webhook with the final result. The handler verifies it, deduplicates by PSP event ID, and in **one transaction**: transitions the payment with a conditional update, writes balanced ledger entries, and inserts an outbox event.
8. The idempotency record is completed with the final response. The order service consumes `PaymentSucceeded` and confirms the order.

## Deep dives

### 1. Idempotency end to end

There are three different retry loops, and each needs its own key:

| Retry by | Key | Effect |
| --- | --- | --- |
| Checkout → us | Client's `Idempotency-Key` | Same payment returned; no second payment created |
| Us → PSP | Our `payment_id` | PSP returns the original charge; card not charged twice |
| PSP → us (webhooks) | PSP event ID (`processed_webhooks`) | Same webhook applied once |
| Kafka → consumers | Our event ID | Each consumer applies each event once |

Server-side, the key is claimed with `INSERT … ON CONFLICT DO NOTHING` in the same database as the payment, so "claim key" and "create payment" can't disagree.

### 2. Timeouts and unknown outcomes

See [Timeouts & unknown outcomes](#diagram/unknown-outcome).

The dangerous case is a timeout talking to the PSP: the charge may or may not have happened.

- **Never treat a timeout as a failure.** Marking it failed and letting the customer retry with a new payment can charge them twice.
- Keep the payment `PENDING` with `outcome_known = false`, and schedule checks: query the PSP by our reference after 30 s, 2 min, 10 min…
- If the PSP has a charge, apply its status. If the PSP has no record, retry the create with the **same** PSP idempotency key — safe by construction.
- Whichever arrives first (webhook or poller) wins; the other's conditional update matches zero rows.

### 3. The state machine

See [States & ledger](#diagram/ledger).

```text
CREATED → PENDING → REQUIRES_ACTION → SUCCEEDED → PARTIALLY_REFUNDED → REFUNDED
                 ↘                  ↘ FAILED
                  → SUCCEEDED
                  → FAILED
```

```sql
UPDATE payments
   SET status = 'SUCCEEDED', version = version + 1, updated_at = now()
 WHERE payment_id = 'pay_77' AND status IN ('PENDING', 'REQUIRES_ACTION');
-- 0 rows → already in a later state (duplicate or out-of-order event): record and ignore
```

Every transition also inserts a `payment_events` row, so the full history of who changed what, when, and why is preserved.

**Out-of-order events:** a late `charge.pending` webhook arriving after `charge.succeeded` must not move the payment backwards — the conditional `WHERE status IN (…)` prevents it.

### 4. Double-entry ledger

Every movement of money is recorded as a **transaction** of entries whose debits equal their credits. For a ₹4,999.00 payment with a 5 % platform fee:

| Account | Debit | Credit |
| --- | --- | --- |
| PSP clearing (money the PSP owes us) | 4,999.00 | |
| Merchant payable (we owe the seller) | | 4,749.05 |
| Platform fee revenue | | 249.95 |
| **Total** | **4,999.00** | **4,999.00** |

Later events add more transactions: PSP settlement moves money from `psp_clearing` to `bank`; PSP fees debit `psp_fee_expense`; a payout debits `merchant_payable` and credits `bank`; a refund adds **reversing** entries.

Rules:

- **Append-only.** Never update or delete an entry. Mistakes are corrected with new entries, so history is never lost.
- **Balanced.** Enforce `sum(debit) = sum(credit)` per `txn_id` (check in code, verify with a database constraint or a periodic job).
- **Balances are derived** from entries (cached for speed, but always recomputable).
- **Atomic with the status change:** the ledger entries, the status transition and the outbox row commit in one transaction.

### 5. Reconciliation

See [Reconciliation](#diagram/reconciliation).

Every day (or more often), ingest the PSP's settlement report and the bank statement, normalise them to minor units, and match each line to our ledger by PSP reference, amount, currency and date.

- **Matched** (~99.9 %): done.
- **Auto-fixable:** a charge the PSP reports as succeeded but that we still have as `PENDING` (lost webhook) → apply the transition; small fee differences → adjusting entries.
- **Unexplained:** our `SUCCEEDED` payment missing at the PSP (a real bug), amounts that don't match, unknown chargebacks → finance ops queue.

Reconciliation is the last line of defence: whatever bug slips past idempotency and state machines shows up here within a day.

### 6. Sagas with other services

Checkout spans order, inventory and payment. The payment service doesn't call them synchronously in a distributed transaction; it publishes events through the outbox, and the order saga reacts (confirm, or release inventory and cancel). A refund is a compensation step in the same pattern. See the E-commerce topic.

### 7. Refunds, payouts, chargebacks

- **Refunds** are their own idempotent operations with their own state machine and PSP idempotency key; the ledger records reversing entries. The sum of refunds can never exceed the captured amount (check under a row lock on the payment).
- **Payouts** run in batches after a holding period: compute each seller's `merchant_payable` balance from the ledger, create a payout record (idempotent per seller per period), send it through the bank or PSP payout API, and record entries.
- **Chargebacks** arrive from the PSP as disputes; record entries that move money back from the merchant and, if the merchant's balance is insufficient, from a platform loss account.

### 8. Multiple PSPs

- Route by card type, region, cost, and recent success rate.
- Fail over to another PSP when one is down — **but only for new payments**. A payment whose outcome is unknown at PSP A must be resolved with PSP A first, or the customer could be charged by both.

## Security and compliance

- **PCI DSS:** card numbers are entered into PSP-hosted fields and tokenised; our systems only handle tokens, which shrinks compliance scope dramatically.
- Encrypt sensitive data at rest; strict access control; every access to payment data audited.
- **Webhooks:** verify the HMAC signature and timestamp (reject old ones to prevent replay); deduplicate by event ID.
- **Fraud:** velocity limits per card/device/account, device fingerprinting, risk scoring, and 3-D Secure for risky payments (which also shifts chargeback liability to the issuer).

## Scaling and reliability

- 12–100 TPS fits on one well-tuned PostgreSQL primary with synchronous replication to a standby in another zone. If volume grows 100×, shard by merchant or account.
- Keep the payment service stateless; all state is in the database.
- Durable queues with retries and dead-letter queues for manual review.

### Failure modes

| Failure | Impact | Handling |
| --- | --- | --- |
| Client retries checkout | Possible duplicate payment | Client idempotency key returns the original |
| PSP timeout | Outcome unknown | Poll PSP; retry with the same key; never assume failure |
| Lost webhook | Payment stuck `PENDING` | Poller; reconciliation auto-fix |
| Duplicate / out-of-order webhooks | Wrong state | Dedupe by event ID; conditional transitions |
| DB primary fails | Payments pause | Failover to the synchronous standby; no committed data lost |
| Bug writes unbalanced entries | Books off | Balance check rejects the transaction; reconciliation flags it |
| PSP outage | Payments fail | Route new payments to another PSP |

## Observability

- Payment success rate by PSP, method, issuer, region (a sudden drop often means a PSP or bank problem).
- Count of payments with unknown outcome older than N minutes (should be ~0).
- Webhook processing lag; duplicate webhooks detected.
- Ledger balance check results; reconciliation match rate and open exceptions.
- Latency of the synchronous path.

## Trade-offs to discuss

- **Synchronous vs asynchronous confirmation:** synchronous responses give better UX; webhooks are the source of truth. Use both and make them converge via conditional transitions.
- **Strong consistency** is non-negotiable for payments and the ledger; analytics and dashboards can be eventual.
- **Build vs buy:** PSPs handle card networks, 3-D Secure and much of PCI; you still own idempotency, the state machine, the ledger, payouts and reconciliation.
- **Authorise-then-capture vs immediate capture:** authorise at checkout and capture at shipping avoids refunds for items that can't ship, but authorisations expire (typically 7 days).

## Interview follow-up questions

- **Why not just use a `balance` column?** Updating balances in place loses history and makes errors unrecoverable; a ledger records every movement and lets you recompute balances.
- **How do you handle currency conversion?** Record both amounts and the FX rate on the transaction; FX gains/losses go to their own ledger account.
- **What happens if the same idempotency key is reused with a different amount?** Reject with `422` — the stored request hash doesn't match.
- **How long do you keep idempotency keys?** Longer than any client's retry window (24 hours is common); the payment itself is permanent.
- **How would you test this?** Fault injection: drop PSP responses, duplicate and reorder webhooks, kill the service between steps — then assert no double charges, no lost payments, and a balanced ledger.
